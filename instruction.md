# Make scheduled-task promotion durable

The checkout in `/app/huey` is Huey 3.4.0. Its SQLite consumer can lose delayed jobs when moving a due batch into the ready queue: after a failed queue write, a job may be present in neither place. Repair this transition and expose it as `Huey.promote_schedule(timestamp=None)` so callers and the consumer use the same operation. The return value is the integer number of promoted rows. This work strengthens the existing behavior; it does not claim that the upstream release already provides transactional promotion.

For `SqliteHuey`, one call must have these observable semantics:

* Select every scheduled row belonging to this Huey queue whose stored timestamp is at most the supplied datetime, including the boundary. An omitted timestamp uses Huey's normal clock. Process eligible rows in stored timestamp order, with schedule row id breaking ties. An empty selection returns zero.
* Promote the entire eligible batch exactly once or leave its durable database state unchanged. Decode and prepare every selected task using the configured registry and serializer, resolve task expiration as ordinary enqueue does, preserve task metadata (including ids, arguments, retries, chains and priority), and put it into the ready queue. Ready-queue priority and FIFO behavior must remain unchanged. Separate schedule rows with identical serialized tasks are separate jobs; do not deduplicate by task id or payload.
* If decoding, encoding, any queue insertion or schedule deletion, or transaction completion fails, raise an exception to the caller, preserve all selected schedule rows, preserve the pre-existing ready queue, and emit no enqueue notifications. A subsequent call after the fault is removed must succeed. This includes batches larger than 500 rows and process termination before commit. No partial transfer or separate durable side file is acceptable.
* Concurrent schedulers using separate connections or processes against the same database must neither lose nor duplicate a scheduled row. Their successful return counts sum to the number actually transferred. Other queue names, future schedule rows, result/revocation data, and counters must remain intact.
* Emit one existing `SIGNAL_ENQUEUED` notification per promoted row, in the selection order, only after successful commit and after releasing internal storage locks. A receiver must be able to read the complete durable batch using another database connection, call this Huey storage's read methods, and schedule another task without deadlock. Receiver failures follow Huey's existing signal exception-isolation behavior and cannot undo a committed batch. Tasks scheduled by receivers are handled on the next promotion, not added to the completed batch.

`Scheduler.loop(now=...)` must use this operation. It must log a promotion failure, remain usable, and retry the still-scheduled jobs on a later iteration. Successful scheduled promotion, periodic task dispatch, and the existing consumer timing behavior must continue to work. Preserve the configured scheduler cadence after both successful and failed promotion, accounting for elapsed work when waiting for the next iteration. Periodic checks retain their normal interval; after a long stall, skip missed checks rather than rapidly enqueueing duplicate periodic jobs for the current minute. For non-SQLite backends, provide the same new public entry point using the existing read-schedule/enqueue behavior; the new database atomicity guarantee applies only to SQLite. The in-memory backend must still schedule and enqueue ordinary tasks correctly.

Keep the existing `Huey.read_schedule()` and storage `read_schedule()` APIs and their destructive-read behavior for callers that explicitly use them. Preserve existing SQLite tables and their readable data; this change must work on a database created by the unmodified checkout without a migration or manual data cleanup. A malformed due payload or an unregistered task must remain recoverable in the schedule after a failed promotion, rather than being silently discarded.

The repair must also compose with a caller-owned SQLite transaction. Applications may use the existing `with huey.storage.db(commit=True) as cursor:` context to combine promotion with ordinary reads, schedule additions, result writes and counter changes. These contexts may nest on the same storage instance and thread:

* An inner successful write scope must not commit its parent's work. Its changes are visible through the same storage instance, but remain invisible to another connection until the outermost write scope commits. A promotion returns the number it moved in that scope; that count is tentative until the enclosing transaction commits. A second promotion does not transfer the same rows again.
* An ordinary failed inner write scope rolls back only that scope, including promotions and ordinary storage operations within it. The caller may catch the error inside the outer scope, continue using that transaction, and retry. A failure escaping the outer scope rolls back all its work. These rules apply to exceptions derived directly from `BaseException` as well as ordinary exceptions, and to failures while completing a write scope. SQLite's own whole-transaction rollback has the distinct behavior specified below. After the fault is removed, the connection must remain usable.
* Enqueue notifications for promoted rows are deferred until the outermost write transaction successfully commits. Discard the notifications belonging to any rolled-back scope; preserve notifications belonging to surviving scopes. Emit them in successful promotion-call order, and in row-selection order within each call. During dispatch another thread must be able to use this same storage instance, and receivers must see the complete committed state. Never emit a notification for an ultimately rolled-back promotion.
* Nested `db(commit=False)` reads must see the surrounding transaction's tentative state. A `close=True` request on any nested `db` context must take effect only after the outermost active `db` context finishes; it must not invalidate a still-active parent's cursor. Distinct threads sharing one storage instance must not join or roll back each other's transactions. Existing separate-process guarantees still apply.

The same transaction composition must work across distinct `SqliteHuey` storage instances pointing to the same regular SQLite file. This supports an application that promotes jobs for several queue names together with their result/counter updates as one unit of work:

* On the same thread, operations through any such instance join the currently active database scope for that file. This includes nested reads and writes, instances created while the scope is active, and equivalent absolute, relative and symbolic-link paths. Queue names remain separate, and each Huey uses its own registry, serializer and signal receivers. A successful inner scope cannot publish any participant's work early; a failed inner scope rolls back changes made through all participants in that scope, while preserving its parent's changes. An outer failure, including a rejected commit, restores all participating queues and discards their pending notifications. Recovery and retry must work through any participant.
* Creating an instance or requesting `close=True` through a participant must not close a connection used by an active parent cursor. The requested connection close occurs after the outermost active database context for that file finishes. Other threads using another instance for the same file must wait for the current write scope to finish and must not join it or have their work rolled back by it.
* For promotions committed together, notifications follow promotion-call order across all participating queue names. Dispatch must release every lock that could prevent another thread from accessing that file through a participant. If a receiver synchronously calls promotion again for the same file, that new operation must commit and return its count normally, but its notifications go behind all notifications already awaiting dispatch for that file on this thread. Drain this work before the initiating outermost call returns; do not recursively interleave the new notifications into an older committed batch.
* Different database files have independent transaction and notification lifetimes, even when queue names match. A nested operation on another file may commit and notify immediately; rolling back the first file cannot undo or suppress that work. This task does not ask for an atomic transaction spanning different files.

Serializer callbacks may synchronously reenter application code during preparation. For example, a custom serializer can read scheduling state, update bookkeeping, add scheduled jobs, or promote a related queue. The SQLite operation must support these finite Python callbacks during both decoding and encoding:

* Each promotion invocation selects its due batch at entry, excluding rows already selected by still-preparing ancestor invocations for that file. It claims the whole selected batch before invoking any serializer. Claimed rows remain visible to ordinary schedule read/count methods until their transfer, but nested promotion through any same-file alias must not select them again. A nested call with no unclaimed eligible rows returns zero. Jobs added during preparation do not join an already selected batch; a nested or later invocation can select them. Counts belong to each invocation's own batch, without double counting.
* Reentry can form cycles across queue names and aliases, while retaining each participant's own serializer, registry and receivers. Same-file nested preparation and its result/counter/schedule writes obey the existing savepoint rules: a caught nested failure discards only that nested call and its descendants, releases their claims, and permits retry while the enclosing batch remains claimed. Failure of the enclosing preparation rolls back all of its same-file descendants. Successfully committed work on another database file remains independent.
* Deferred notifications follow successful invocation-entry order, with an enclosing promotion's complete row-ordered batch before batches promoted from its serializer callbacks. Failed calls contribute no notifications or occupied ordering positions. None of these notifications may run before the enclosing write transaction commits. Claims must be gone when postcommit signal receivers run, including when a newly scheduled row reuses a deleted schedule row id. Existing postcommit reentry still appends its notifications behind all already pending batches.
* If a serializer catches an error that aborted the entire SQLite transaction, the enclosing promotion must still fail without performing later queue inserts or schedule deletes in autocommit mode. Restore the pre-transaction durable state and suppress that transaction's notifications; normal recovery starts after its invalid write scopes unwind.

Within preparation callbacks, supported operations are ordinary storage reads, `add_schedule`, result/counter operations, and `promote_schedule`, including their nested `db` scopes. Callbacks do not destructively read or flush the schedule, mutate selected rows with raw SQL, close connections, or run inside a native SQLite callback. They do not change the existing filename, connection-option or fork boundaries. There is no new guarantee for serialization reentry on non-SQLite backends.

SQLite may itself abort the entire transaction, for example when a trigger executes `RAISE(ROLLBACK, ...)`. A savepoint cannot preserve its parent's changes in that situation. All still-enclosing write scopes for that file become invalid: even if the caller catches the triggering error, further storage reads, writes and promotions through any participant must raise, and a normally exiting enclosing write scope must raise instead of reporting a successful commit. Do not silently start an independent transaction inside an invalid enclosing scope. Preserve the pre-transaction durable state and discard every notification from the aborted transaction. Detect an abort issued through a yielded cursor even when its exception was caught and no later storage call occurs. After the outermost write scope has unwound, a fresh write must work, including inside a still-open surrounding read-only context. Keep notifications from earlier successful transactions and other files intact. Ordinary statement aborts such as `RAISE(ABORT, ...)` leave the SQLite transaction alive and retain the existing local rollback/retry rules; do not invalidate a healthy parent merely because an SQL statement raised. After catching a whole-transaction abort, callers use storage APIs or leave their contexts; direct raw SQL until the invalid write scopes unwind is outside this requirement.

The SQLite repair must also work with Huey's POSIX `fork` process model. Live Huey objects can be inherited by child processes and descendants. Child operations must use fresh process-local SQLite connection state and coordination, without inheriting parent read-context nesting, pending notifications or a notification-dispatch-in-progress flag. Parent connection-local temporary tables must not appear in a child's new session. Inherited and newly created instances for the same file must still compose within that child, using their own registries and receivers. A child calling `storage.close()` on an inherited object must not invoke native SQLite cleanup on a connection opened in its parent; subsequent child storage operations must remain usable. The parent's connections, temporary state and notifications must remain usable and unaffected.

At the moment of fork there is no active SQLite write transaction, executing SQLite call or partially consumed SELECT. There may be a read-only `db` context held by the forking thread or another parent thread, including notifications from a completed write deferred by that read context; fork may also occur inside a postcommit signal receiver. The child runs a separate multiprocessing target and does not unwind the parent's inherited context-manager stack or directly use an inherited raw cursor/connection. Its database work begins after the parent has released its read context. Such work must not hang on a copied lock or suppress its own notifications, and every descendant process has the same obligations. Forking during an active SQLite write transaction or native SQLite callback is outside scope.

Callers do not issue raw transaction-control SQL or use `storage.close()` inside a context they entered in their current process. Same-file participants use compatible SQLite connection options. URI databases, hard-link aliases, in-memory database sharing, changing filenames while a context is active, and competing threads acquiring multiple database files in opposite orders are outside the cross-instance requirement. Non-SQLite backends keep their existing transaction behavior; exercise the new promotion entry point for both MemoryHuey and FileHuey using their existing scheduling and enqueue semantics.

Make your changes under `/app/huey/huey/`. Do not replace the project with a stub, depend on another Huey installation, or modify the task harness. Python 3.12 and SQLite are available; this repair needs no external service. You may add private helpers and choose the implementation freely. The deliverable is the repaired source tree; no report or precomputed database is required.
