# Make scheduled-task promotion durable

The checkout in `/app/huey` is Huey 3.4.0. Its SQLite consumer can lose delayed jobs when moving a due batch into the ready queue: after a failed queue write, a job may be present in neither place. Repair this transition and expose it as `Huey.promote_schedule(timestamp=None)` so callers and the consumer use the same operation. The return value is the integer number of promoted rows. This work strengthens the existing behavior; it does not claim that the upstream release already provides transactional promotion.

For `SqliteHuey`, one call must have these observable semantics:

* Select every scheduled row belonging to this Huey queue whose stored timestamp is at most the supplied datetime, including the boundary. An omitted timestamp uses Huey's normal clock. Process eligible rows in stored timestamp order, with schedule row id breaking ties. An empty selection returns zero.
* Promote the entire eligible batch exactly once or leave its durable database state unchanged. Decode and prepare every selected task using the configured registry and serializer, resolve task expiration as ordinary enqueue does, preserve task metadata (including ids, arguments, retries, chains and priority), and put it into the ready queue. Ready-queue priority and FIFO behavior must remain unchanged. Separate schedule rows with identical serialized tasks are separate jobs; do not deduplicate by task id or payload.
* If decoding, encoding, any queue insertion or schedule deletion, or transaction completion fails, raise an exception to the caller, preserve all selected schedule rows, preserve the pre-existing ready queue, and emit no enqueue notifications. A subsequent call after the fault is removed must succeed. This includes batches larger than 500 rows and process termination before commit. No partial transfer or separate durable side file is acceptable.
* Concurrent schedulers using separate connections or processes against the same database must neither lose nor duplicate a scheduled row. Their successful return counts sum to the number actually transferred. Other queue names, future schedule rows, result/revocation data, and counters must remain intact.
* Emit one existing `SIGNAL_ENQUEUED` notification per promoted row, in the selection order, only after successful commit and after releasing internal storage locks. A receiver must be able to read the complete durable batch using another database connection, call this Huey storage's read methods, and schedule another task without deadlock. Receiver failures follow Huey's existing signal exception-isolation behavior and cannot undo a committed batch. Tasks scheduled by receivers are handled on the next promotion, not added to the completed batch.

`Scheduler.loop(now=...)` must use this operation. It must log a promotion failure, remain usable, and retry the still-scheduled jobs on a later iteration. Successful scheduled promotion, periodic task dispatch, and the existing consumer timing behavior must continue to work. For non-SQLite backends, provide the same new public entry point using the existing read-schedule/enqueue behavior; the new database atomicity guarantee applies only to SQLite. The in-memory backend must still schedule and enqueue ordinary tasks correctly.

Keep the existing `Huey.read_schedule()` and storage `read_schedule()` APIs and their destructive-read behavior for callers that explicitly use them. Preserve existing SQLite tables and their readable data; this change must work on a database created by the unmodified checkout without a migration or manual data cleanup. A malformed due payload or an unregistered task must remain recoverable in the schedule after a failed promotion, rather than being silently discarded.

The repair must also compose with a caller-owned SQLite transaction. Applications may use the existing `with huey.storage.db(commit=True) as cursor:` context to combine promotion with ordinary reads, schedule additions, result writes and counter changes. These contexts may nest on the same storage instance and thread:

* An inner successful write scope must not commit its parent's work. Its changes are visible through the same storage instance, but remain invisible to another connection until the outermost write scope commits. A promotion returns the number it moved in that scope; that count is tentative until the enclosing transaction commits. A second promotion does not transfer the same rows again.
* A failed inner write scope rolls back only that scope, including promotions and ordinary storage operations within it. The caller may catch the error inside the outer scope, continue using that transaction, and retry. A failure escaping the outer scope rolls back all its work. These rules apply to exceptions derived directly from `BaseException` as well as ordinary exceptions, and to failures while completing a write scope. After the fault is removed, the connection must remain usable.
* Enqueue notifications for promoted rows are deferred until the outermost write transaction successfully commits. Discard the notifications belonging to any rolled-back scope; preserve notifications belonging to surviving scopes. Emit them in successful promotion-call order, and in row-selection order within each call. During dispatch another thread must be able to use this same storage instance, and receivers must see the complete committed state. Never emit a notification for an ultimately rolled-back promotion.
* Nested `db(commit=False)` reads must see the surrounding transaction's tentative state. A `close=True` request on any nested `db` context must take effect only after the outermost active `db` context finishes; it must not invalidate a still-active parent's cursor. Distinct threads sharing one storage instance must not join or roll back each other's transactions. Existing separate-process guarantees still apply.

Callers do not issue raw transaction-control SQL, use `storage.close()` inside an active context, or require transactions spanning different storage instances. Non-SQLite backends keep their existing transaction behavior; exercise the new promotion entry point for both MemoryHuey and FileHuey using their existing scheduling and enqueue semantics.

Make your changes under `/app/huey/huey/`. Do not replace the project with a stub, depend on another Huey installation, or modify the task harness. Python 3.12 and SQLite are available; this repair needs no external service. You may add private helpers and choose the implementation freely. The deliverable is the repaired source tree; no report or precomputed database is required.
